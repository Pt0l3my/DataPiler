# What the designers settled from design 0001

The owner's decisions are in [../DECISIONS.md](../DECISIONS.md); this is the designers' own log, one entry each (S1
onwards), for points design 0001 left to us or suggested, and for what the build and its fix rounds settled (S15
onwards). Each can be reopened; one that would change an owner's rule becomes a DP question instead.

| # | Point | Settled | Why |
|---|---|---|---|
| S1 | The shape (§1) | As design 0001 §1: `DataPiler.exe`, `DataPiler.ps1`, `datapiler.py` with its modules, `soapstone/`, `requirements.lock`, `launcher-src/`, and the workspace, share, logs and jobs folders kept out of the repository | It is the request's shape and Jobrunner's, with the PowerShell window |
| S2 | Python's two libraries (§4) | A local `.venv` made at the first start from `requirements.lock` (wheels only, a sha256 for every file), after the owner answers Y; N starts DataPiler without the server link | One download, checked by hash, with the owner's consent; no binaries redistributed |
| S3 | The gRPC client (§4) | Message classes only, generated once from SoapstoneLib's `.proto` files at a pinned commit, committed with its MIT notice; each allowed call built by hand from a fixed table, so no stub for any other call exists; a test fails if any other method name appears in the code | The allowlist is enforced by construction, not by care |
| S4 | The exe's build (§3) | A GitHub Actions workflow on Windows builds the launcher on a tag the owner pushes and attaches it with its sha256 to the release; the `BUILD.md` route stays for a local build | For a public repository, anyone can see the exe comes from the source |
| S5 | Floats in share files (§7.1) | Allowed: any finite JSON number; NaN and infinities refused | A finite number cannot carry text; some character fields are floats |
| S6 | Labels against the text database (§7.2) | The guard's text check skips values that are exactly one of DataPiler's fixed labels; the label list is checked against the text database once it is built, and a label found there is renamed | Otherwise a label that happens to be a game word fails forever |
| S7 | "The game is closed" (§7.3) | Neither `eldenring.exe` nor `start_protected_game.exe` is running, by name and, with the game's folder known, by path | Easy Anti-Cheat's launcher starts the game |
| S8 | Map loading (§7.4) | Loads maps in batches, and asks before loading more than ten | `OpenResource` changes Smithbox's state and memory, not its data |
| S9 | Smithbox's server switch (§7.5) | Read and shown, never written; at the end of a session the Status card says how to switch it off | Smithbox's files are read only |
| S10 | Guided exports (§7.6) | Accepted by shape (Smithbox's text export format, the container, the language), never by file name; anything else stays in the inbox with the reason | A file name proves nothing |
| S11 | Sharing logs (§7.7) | **Copy for sharing** on the Terminal tab runs the guard's text and owner checks over the lines first | Logs are masked by construction, but a check costs nothing |
| S12 | The network (§7.8) | None after the first start, and none at the first without the owner's Y; the page loads nothing from elsewhere | DP3, the owner's emphasis on privacy and security |
| S13 | Versions (§7.9) | A job may say `"needs": "<version>"`; an older DataPiler refuses it, saying so | Jobs are written ahead of releases |
| S14 | The repository's own check (§7.10) | A CI check fails any change that adds a file under `workspace/`, `share/`, `logs/` or `jobs/`, a share file, or a file the privacy sweep flags | It catches a forced add |
| S15 | The launcher's wait (§3, DP7) | A second start, while DataPiler runs or its window is still starting, waits up to 60 s for that one's page; the first start waits for its own app's port file for as long as the window it started is open, with no time limit (F3 of the build's review) | Differs from design §3's 60 s on purpose: a first start asks the owner Y or N there and may download the libraries, which no bound fits, and the window itself says what it is doing |
| S16 | The owner's folders on the page | The Settings form shows the folders the owner typed, as typed, on the local page only (`127.0.0.1`, with the per-start token); Status shows them only in a check's "?" detail. Logs show them as placeholders (`<GAME>`, `<SMITHBOX>`, `<PROJECT>`, `<WORKSPACE>`, `<SHARE>`), and no folder reaches a share file (check 4) or a copied log (Copy for sharing) | A form must show what it edits; the page never leaves the PC, and everything that can leave it is masked or checked |
| S17 | Placements' maps in 0.1 (P5) | `load_maps` names its maps by id: `"all"` is refused, as none of the seven allowed calls lists every map. `read_placements` with `"all"` reads the maps already loaded in Smithbox; Extract's Map placements row does the same, and loads maps first only when the owner asks | No call to guess a map list from; DataPiler never invents ids |
| S18 | DP8: what reaches `write_share` (§6) | Every table carries its lineage. Raw: what `fetch_rows` and `read_placements` make, and a filter, a distinct or a `join_names` of a raw table. Narrowed: a filter keeping only the named rows (`named` is true) after `join_names`, or a filter on an explicit list of 1 to 1,000 row ids (`ids`, matched against the table's row id, `id` or `entityId`, or `key`: `npcParamId` for placements). Aggregate: a `count`, unless it counts a raw table by its row id or by a column that holds other tables' ids (`fields.REFERENCES`: `nameId`, `msgId`; a placement's `npcParamId`, `talkId` and `model`): one row per id stays raw (fix round 3, P15). `write_share` refuses a raw table, naming the operation and the rule. Extract's own share files hold counts only, never an id; Extract writes the workspace and at most that summary ("Goes to": Workspace + share, counts only) | The owner's rule (DP8); the explicit list is the "rows picked for a purpose" a job can state |
| S19 | DP8: check 6, Coverage (§6) | The guard refuses a share file in which one table, or its tables from one game table together, cover more than half of that game table's rows: a param's rows as Smithbox lists them (each row id once), or the placements of every map the job read, each map once. Each table is measured by its rows (one per row of its source, or one per group of a count or a distinct), except one that keeps a param's row id while no row id repeats among the rows its `fetch_rows` read, which is measured by its distinct ids, so the same rows in two tables count once; placements are always measured by their rows, as their entity ids can repeat. Only a table of counts alone (a count's `count` without its groups) is not measured. The runner hands the guard each table's counts and source (the param, or `placements`), from the job's lineage. The share format is unchanged by it: the counts are kept in `workspace/share-counts.json` (`datapiler-share-counts/2`) by file name and sha256, so Outputs runs check 6 again, and a file DataPiler did not write, or one changed since, fails it. Each share file is measured on its own, never with the files already in `share/` (fix round 3: a file's answer then never changes after it is written, and files moved out of `share/` would not be seen anyway). A failure names the check and the table at which its game table passes half (`tables[2]`), never a value | The backstop DP8 asks for, behind S18's rule; local numbers never leave the PC |
| S20 | Check 3 over values only (P12) | Check 3 reads string values, never the share format's own keys, which come from the format and are checked by check 1. A value that is exactly one of DataPiler's fixed words is skipped: its labels (S6), its column types and enum values, the column names its operations make (`fields.PARAMS`'s fields, the placements' columns, `named` and `count`), the expansion's source and the format constant. Table names, job ids and every other value stay checked | One ordinary description in the text database ("named", "arrows", "counted") refused every share file; DataPiler's own words are not game text wherever they sit |
| S21 | The expansion (P2) | A Settings value the owner states: Expansion installed, yes or no, not stated at first. A share write with it not stated is refused with the line "whether the expansion is installed is not stated yet - set Expansion installed in Settings (yes or no)". The provenance records the statement (`expansion`) and that it is the owner's (`expansion_source`: `owner`). A file check, once marker files are confirmed, only shows a hint on Status, never decides | The files that mark the expansion are not confirmed; the owner knows their own install |
| S22 | The names' wrappers (P3) | ER01's leads are built in: the character names in wrappers 18, 328 and 428 and the place names in 19, 329 and 429, of the item containers (`item`, `item_dlc01`, `item_dlc02`, which the Place names row now waits for too). `join_names` uses a set only if at least half of the non-negative name numbers of the rows it joins resolve in it; otherwise it fails with the share that did. The share file's provenance records, per set joined, the wrappers, that they were verified, and the share that resolved (the lowest, rounded down) under `names` | Leads, not facts: they are used only once the owner's own data bears them out (EldenNet O48) |
| S23 | Python's three libraries (P13) | grpcio needs `typing-extensions` (PSF-2.0), installed with `--no-deps` from the lock like the other two. README, NOTICE, the page and the window's question name it as "grpcio and protobuf, and typing-extensions, which grpcio needs"; S2's "two libraries" reads three. DataPiler imports grpcio and protobuf only, in `datapiler/link.py` and `soapstone/` | A dependency of a dependency is still downloaded to the owner's PC, so it is named with its licence. DP4's accepted cost names two; the third is recorded here for the owner |
| S24 | The release (S4) | Besides `DataPiler.exe` and its sha256, the draft release carries one zip of the whole app, `DataPiler-<version>.zip`: the tagged source as `git archive` makes it, with the built exe and `THIRD-PARTY-NOTICES.txt` placed in it, and its sha256 | The owner downloads one file; the exe's notices go wherever the exe goes; publishing stays the owner's act |
| S25 | Check 3 across separators and accents (fix round 3) | Check 3 compares each string value with the texts twice: case-folded as it is, and normalised (decomposed, accents dropped, case-folded, each run of spaces, `_`, `-` and other signs one space) against the texts normalised the same way, with the same three rules (equal; at 4 or more characters inside a text; holding a text of 4 or more characters). Copy for sharing's check of the log lines does the same | A table name (`a-z`, `0-9`, `_`) or a job id (`a-z`, `0-9`, `-`) can hold neither a space nor an accent, so a name is naturally written `white_mask_varre`; a value with no sign between its words compares as before, so S20's ordinary words are unaffected |
| S26 | Check 4's owner words (fix round 3) | The user name and the PC name are each found from their letters and digits, with any signs between them or none (`[\W_]*`), as a whole word, case-folded: `DESKTOP-XXXXXXX` as `desktop_xxxxxxx` too, and a two-part user name with `_`, `-` or nothing between. Copy for sharing uses the same patterns (`guard.owner_patterns`) | A PC name's `-` cannot stand in a table name, and a user name's space in neither a table name nor a job id |

**S14, note of 2026-11-08** (the build's review, SEC-8 and F9). CI cannot run the privacy sweep itself: it lives in
EldenNet, and its personal list never leaves the owner's PC. So `tools/repocheck.py` carries the sweep's rules that
need no list of anyone's names: besides the run-time folders, game files, share files and IP addresses, a user's
folder (unless its name is a placeholder or a generic one) and an e-mail address other than a noreply or an example
one. The owner's personal words stay with the sweep's pre-push gate.

**S4, note of 2026-11-08.** This session's git proxy refuses to push tags (HTTP 403), so the assistant cannot start a
release. The release workflow therefore also has a **Run workflow** button (`workflow_dispatch`, no inputs): the owner
chooses the branch, the version comes from `VERSION`, and the draft release targets that commit for tag
`v<version>`, which GitHub creates when the owner publishes it; a tag that already exists is refused. Publishing stays
the owner's act either way.
